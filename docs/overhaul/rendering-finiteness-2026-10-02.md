The foliage rim shader had a reproducible floating-point domain error. On Chrome 150.0.7871.186, ANGLE OpenGL ES / Radeon RX 9060 XT, normalizing the vector `(1/31, 11/33, 12/37)` and taking its dot product with itself returned `1.0000001192092896`. The shipped expression then evaluated `pow(-0.0000001192092896, 2.8)` and returned NaN. Clamping only the power's base to zero fixes that endpoint without changing its valid-domain values. The material program key advances from v3 to v4. Source change: `31ecbd9`.

This is a demonstrated shader defect, but it is not a confirmed reproduction of the player's black-pixel screenshot. The original and fixed full-scene scans both returned finite values in all 96 controlled cases. The private player image remains outside this repository; all committed game captures are our own.

The numerical regression compiles the production expression verbatim, replacing only its cosine input for boundary samples. It checks both unit endpoints, one and two Float32 ULPs beyond either endpoint, ordinary interior values, and the actual GPU normalization above. The original shader fails; the fixed shader passes. The nine valid samples are exactly equal before and after. Raw results are [before](evidence/codex-render/rim-before-samples.json) and [after](evidence/codex-render/rim-after-samples.json). GLSL ES 3.00 explicitly leaves `pow` with a negative base undefined; mathematical bounds on normalized vectors do not guarantee those bounds after floating-point rounding. [Khronos specification, section 8.2](https://registry.khronos.org/OpenGL/specs/es/3.0/GLSL_ES_Specification_3.00.pdf).
